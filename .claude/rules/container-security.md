# Container security

A build loads the code of the models' frameworks, such as NeMo, torch and Transformers, and files that run code when they load, such as a pickle or a `.nemo` checkpoint. That code is untrusted: it runs only in containers, and the host treats what they write as hostile. These rules grow with the build's code.

## The host

- **The host runs on its own Python and the standard library, isolated:** the host's side of the build runs under `-I -S -B` and imports only the standard library and the project's own packages, never a library of the steps, such as torch, NeMo, Transformers, onnx or ONNX Runtime. `-I` ignores the environment's Python variables, the user's site directory and the current directory, `-S` leaves the site packages out, and `-B` writes no bytecode into the clone, so that nothing installed on the host, and nothing planted beside the code, runs with the user's rights. The one place that changes `sys.path` is the bootstrap, `src/mostt_model_builder/bootstrap.py`, which the launcher, `model-build.sh`, and every step run by path: it appends the project's `src` and each recipe's, and only a real directory whose name follows the recipe grammar, then runs the entry module it is given. It imports nothing of the packages, since it runs before they are on the path. Check: `tests/test_mostt_model_builder.py` imports the command line under `-I -S -B` and refuses any module from outside the standard library and the package; `tests/test_model_build_launcher.py` checks that the launcher runs the bootstrap under `-I -S -B`; `tests/test_bootstrap.py` checks the paths the bootstrap appends and the entry modules it refuses; `lint-imports` keeps the bootstrap's imports out of the packages.
- **A container step's Python runs under `-I -B`:** the image's own Python, which keeps its site for the libraries the image installed, and nothing from the environment or the working directory, so that a step runs the same code at every build. The host starts it itself, with `--entrypoint` naming the image's Python, `/opt/venv/bin/python` in an image with an environment and the base's `/usr/local/bin/python3.12` in one without, then `-I -B`, the image's copy of the bootstrap and the row's entry module, and never relies on an image's own entry point. Check: `tests/domain/containers/test_container_steps.py` and `tests/adapters/test_docker_engine.py`, on every row.
- **Root is refused:** the bootstrap's first act, before it reads anything, is to exit with status 77 when any of the real, effective or saved user or group ids of its process is 0. A build as root would leave files in the work directory that the user cannot remove, and would give any mistake of the launcher the whole machine. Check: `tests/test_bootstrap.py`, on each of the six ids.
- **uv never builds a package on the host:** `no-build = true` in the host's `[tool.uv]`, in `pyproject.toml` at the root, so that every install takes a wheel by its hash and no package's build code, such as a `setup.py`, runs outside a container; and no other file of the repository is named `pyproject.toml`, `uv.toml` or `uv.lock`, the names by which uv finds a project and its settings, in its working directory or the nearest parent that holds one, and, with `--frozen`, a lock even without a project beside it, so that uv, wherever it runs in the clone, `images/` included, finds the root's project, settings and lock alone. Check: `tests/test_project_manifests.py` holds the host's `[tool.uv]` to exactly `package = false` and `no-build = true`, and the tracked files of these names to the root's `pyproject.toml` and `uv.lock`; `tests/test_lockfiles.py` runs the locks' check on `uv.lock`, which refuses a package without a wheel that installs on Python 3.12 for Linux x86-64.
- **No uv on the host finds the images' environment:** its manifest allows a build, `no-build = false`, since one of its packages is published as an sdist alone, so a resolution or an install of it on the host would run that package's build code with the user's rights. The manifest is named `images/environment.toml` and the lock `images/environment.lock`, none of the names that "uv never builds a package on the host" keeps for the root, for two reasons: uv finds a project by its `pyproject.toml`, so no uv looks for the manifest, whatever its version, and uv refuses it as a requirements file; and with `--frozen`, uv 0.13.7 uses a `uv.lock` in its working directory even without a `pyproject.toml` beside it, an experimental feature, for a lock at revision 5 or later, so a lock of that name in `images/` would let `uv sync --frozen` there install the images' environment on the host. Both take uv's names, `pyproject.toml` and `uv.lock`, only inside a container: in the `lock` step's `/tmp`, where `./model-build.sh lock` resolves its lock, and in each image that installs from that lock. No command, gate step, CI step or hook gives either to uv on the host: the gate reads them as text. Check: `tests/test_project_manifests.py`, on the names of the tracked files; `tests/test_recipe_listing.py`, which holds each image's copies of the manifest and of the lock to their accepted forms; `tests/steps/test_lock_resolution.py`, on the copies that the `lock` step gives uv and the name of the lock it writes; review, the commands.
- **The host reaches the network only to fetch the sources, resolve the images' lock, build the images, publish the candidate and check a published revision:** `fetch` runs curl on the host, `lock` runs its container on Docker's default bridge, `docker build` has Docker's network, `publish` runs its container on Docker's default bridge, and `check-published` runs curl on the host, without a token, to read the listing of a published revision and to download its files as `fetch` downloads a source; every other step runs with `--network none`, so that no code of a model and no reader of its files can reach the outside world. `check-published` holds the repository and the revision to their grammars before any request, reads at most 1 MiB of the listing, within 60 s, and parses it strictly, `domain/publication/published_tree.py`: its depth checked before it decodes, an array of at most 1024 entries, each one's `type`, `path` and `size` alone read and typed, the Hub's other fields skipped; it refuses a directory, a missing file, a file of another size, and any file but the Hub's `.gitattributes` and the build's own, then downloads each file through a pin built by the pins' parser and kept only once its size and its SHA-256 match the build's. Check: `tests/domain/containers/test_container_steps.py` and `tests/adapters/test_docker_engine.py`, on every row and on the `publish` row; `tests/domain/publication/test_published_tree.py`, `tests/application/test_check_published.py` and `tests/adapters/test_curl_downloader.py`, on `check-published`.
- **A source is fetched over HTTPS alone, and kept only once it matches its pin:** each source is pinned in a `sources.toml`, the core's at the root of the clone, by its Hugging Face repository, a revision that is a full 40-digit commit, its path, its size and its SHA-256, and its URL is built only from a pin that the host's parser accepted. curl takes `--disable` first, so that no configuration file of the user's adds an option, then HTTPS alone, redirects included, at TLS 1.2 or later, no globbing, a size bounded by the pin, and `--` before the URL. A download lands in a partial file, which takes its name in the work directory only once its size and its SHA-256 match the pin, and is removed otherwise; a fetched file is left read-only, and is checked again at every fetch. A branch or a tag would let the files change under the same pin, and a file kept unchecked would reach every container that reads it. Check: `tests/domain/sources/test_source_pins.py`, `tests/application/test_fetch_sources.py` and `tests/adapters/test_curl_downloader.py`.
- **A source's name never marks code, a pickle or an archive, unless its pin says it runs code:** the file name of a pin is refused when any of its suffixes, whatever its case, marks code, a pickle, an archive or a format that runs code when it loads, such as `.pt`, `.bin`, `.nemo`, `.py`, `.zip` or `.tgz`: the suffixes that the published files refuse, without `.tar` and `.gz`, since FLEURS ships its audio as `.tar.gz` archives that a container reads member by member. Only a pin that says `runs_code_when_loaded = true`, a boolean and nothing else, may name such a file, and that mark then follows the file to every row that binds it ([Confinement](#confinement)). A file that runs code when it loads must never reach a container that was not built to read it, so it is never fetched unmarked. Check: `tests/domain/sources/test_source_pins.py`, on each refused suffix, on the list of them and on the mark; `tests/test_recipe_listing.py`, which holds every `sources.toml` of the repository to exactly one marked file, the `.nemo` of Parakeet TDT 0.6B v3.
- **The work directory is the user's own, outside the home directory and the clone:** it is given by `--work`, never by a default, and must match `/[A-Za-z0-9._/-]+`, be canonical, exist as a directory and not a link, belong to the user, and have the mode 0700 exactly. It is neither the home directory, nor under it, nor around it, where the home directory is both `$HOME` and the account's home, each canonical, and a missing or relative `$HOME` is refused; and it lies neither under the clone nor around it. Containers write into it and the host binds its files into them, so a work directory that held the home directory or the clone would bring the user's files, secrets or code within their reach, and one that another user could write into would let that user swap a file between its check and its use. The grammar is checked before the path is read, and keeps it free of the characters that Docker's options and a shell read as syntax. Check: `tests/domain/containers/test_work_directory.py` and `tests/application/test_open_work_directory.py`.
- **What a container prints or writes is data, never an instruction:** the host takes no command, path or decision from it beyond what a strict, bounded parser of its own accepts, one parser per kind of file, each with its refusal tests: `domain/containers/step_peaks.py` for every `peaks.json`, `domain/bench/fleurs_check_report.py` for the report of `fleurs-check`, `domain/lock/lock_check.py` and `lock_freshness.py` for the lock that `lock` writes, `domain/acceptance/parity_reports.py` for every parity report, such as the export's against NeMo, which must name the parity the recipe declares, `domain/onnx/conversion_report.py` for the report of the conversions, which must describe the conversions the host asked for, in their order, `domain/onnx/inspection_report.py` for the inspection's report of the candidate's graphs, `domain/onnx/node_placement.py` for the placement summary of a run on the GPU, `domain/publication/publication_report.py` for the report of `publish`, which must name the repository it was asked for and each file it was asked to commit, with the size and the SHA-256 that the verification accepted, and `domain/bench/hypotheses.py` for the lines of every run, which reach the core only through the run's reader, a pure function of its recipe, such as `recipes/parakeet-tdt/src/mostt_recipe_parakeet_tdt/domain/transcripts/run_readers.py` with `token_rendering.py` and `vocabulary.py`. Each parser of JSON refuses a document nested deeper than 32 levels before it decodes it, in a single pass over its characters, since json's decoder recurses once per level and a scan whose cost grew faster than the text would let a container stall the host. An output that no parser of the host reads, such as the name lists of `describe` or the files of the export, is judged as any output, and the host takes nothing from it but its size, which it reports, or, for a file of the candidate, its copy. The name lists that a recipe's tests read from their committed copies go through a strict parser of the recipe's, `recipes/parakeet-tdt/src/mostt_recipe_parakeet_tdt/domain/export/tensor_fixtures.py`, which holds their names, types and shapes to printable ASCII, so that no character a reader cannot see enters the repository through them. A step leaves regular files only, at the top of its output directory, under the names its row declares, each in mode 0640 and within its size bound. The host opens that directory with `O_DIRECTORY | O_NOFOLLOW` once it has judged it, and each file relative to it with `O_NOFOLLOW | O_NONBLOCK`; it judges the file by `fstat`, a regular file owned by 65531, in mode 0640 exactly, without setuid or setgid, within its bound and with a single link, reads through that descriptor only the files that one of its parsers reads, judging every other by its facts alone, and refuses an undeclared entry, so that no link and no swapped file leads it to read what a container chose, and no large output, such as the external data of a model, enters the host's memory only to be measured. What a container prints goes to its log, outside every output directory, through a filter that turns every byte outside printable ASCII, the tab and the line feed into `?`, capped at 16 MiB and drained beyond; on a failure, the terminal shows only the log's last 8 KiB, and the output of `docker build` takes the same path. A container value quoted in a message is shown through `ascii()`. The output can then neither forge the terminal's display nor fill the disk. Check: `tests/domain/containers/test_container_files.py`, `tests/application/test_run_step.py`, `tests/application/test_run_recipe_step.py`, `tests/application/test_convert_variants.py`, `tests/adapters/test_work_files.py`, `tests/domain/containers/test_printable_output.py`, `tests/domain/json_documents/test_json_depth.py` and the refusal tests of each parser, `recipes/parakeet-tdt/tests/domain/export/test_tensor_fixtures.py` and the recipe's tests of its readers included.
- **The token reaches only the publication's container, on its standard input:** a row takes the maintainer's Hugging Face token only when it is the core's row named `publish`, and the step table refuses the token on any other row, as it refuses the network outside `lock`. The token is held to a grammar, `hf_` followed by 8 to 256 ASCII letters and digits (hypothesis: every Hub token takes this form; the trial publication settles it), by `domain/publication/hub_token.py`, whose refusal never quotes the text it refused and whose type shows itself as `HubToken(<hidden>)`. The host gives it to its container as one line on a pipe, `docker run --interactive`, then closes the pipe: never in an argument, the environment, a request, a file or a message, where every process of the user, a log or a crash report could read it, and the Docker adapter refuses a run whose row takes the token without one, or one without. A row that takes no token runs without `--interactive`, its standard input empty. The host replaces every occurrence of the token's bytes in what the container prints, across the boundaries of the chunks it reads, `domain/containers/secret_redaction.py`, before the printable filter, the log and the tail it shows on a failure. Check: `tests/domain/publication/test_hub_token.py`, on its grammar and on refusals that never quote; `tests/domain/containers/test_secret_redaction.py`, a property over streams cut at every boundary; `tests/domain/containers/test_container_steps.py`, which refuses the token on every other row; `tests/adapters/test_docker_engine.py`, on `--interactive`, the token absent from the arguments, and a stand-in program that echoes its standard input into a log that holds only the placeholder.
- **The candidate is the host's own copy, checked whole before any run reads it:** the host copies each file the recipe names from the declared output of its step, through the descriptor of the step's judged directory, into a new file in mode 0444 in a new candidate directory, never a link, and writes the contents the recipe gives itself; as each file streams by, it refuses one whose first 512 bytes carry the signature of code, a pickle or an archive, `domain/formats/file_signatures.py`, whatever its format, and one that fails its format's structural check, `domain/formats/file_formats.py`. The inspection then reads every `onnx` file in a container, every node and every tensor of its main graph, of each subgraph at any depth and of each function, `domain/onnx/model_graphs.py`, and the host refuses a node of an unknown domain or a call to a function the model does not define, a node that holds `metadata_props`, which may name paths of the container, a training graph, which no runtime of the candidate runs, a sparse initializer in any graph, whose weights no rule of the products judges, a tensor outside the external data the contract gives, a constant weight of the conversions' input that is not a plain 2-D initializer, and in the output of the conversion to 8-bit blocks a product of a constant weight left unquantized or a count of `MatMulNBits` other than its recipe declares, each rule following where a file comes from and never its name, `domain/onnx/graph_rules.py`, and external data that a tensor overruns, overlaps, leaves a gap or padding in, or that another `onnx` file names, `domain/formats/external_data.py`. Every row that binds the candidate, each shard of a run included, reads the inspection's report again and judges its rules and every copy of the candidate before its container starts, so that a run never reads a candidate that its inspection refused, never inspected, or that changed since. The inspection is keyed by the SHA-256 of every copy, so its report always describes the bytes it read, and a candidate reused under its key is judged as the host's own copies, then streamed once more through the same checks, its signatures, its format's structure and its SHA-256, against its record, before any row reads it, even when a check was added after it was assembled. A file of the candidate then holds only what its recipe declared, in a form that loads no code, and no container can change it once checked. Check: `tests/application/test_assemble_candidate.py`, `tests/application/test_resolve_build.py`, `tests/application/test_run_recipe_step.py`, `tests/domain/onnx/test_model_graphs.py`, `tests/domain/containers/test_container_files.py`, `tests/domain/formats/test_file_signatures.py`, `tests/domain/formats/test_file_formats.py`, `tests/domain/onnx/test_graph_rules.py` and `tests/domain/formats/test_external_data.py`.

## Confinement

- **The code of a model runs only in a container:** the libraries of the steps, and any file that runs code when it loads, are loaded nowhere else. Nothing is installed on the host for them.
- **A container that loads that code has no network, no privilege and none of the host's secrets:** `--network none`, a read-only root, `--cap-drop ALL`, `--security-opt no-new-privileges`, `--ipc none`, `--log-driver none`, `--ulimit core=0`, `--rm` and `--pull never`; the unprivileged user 65531 in the user's group; and limits on its memory, with its swap at the same value, its processes and its CPUs, each a positive integer within its bounds, since Docker reads 0 or -1 as no limit. Its `/tmp`, and its `/scratch` where its row asks for one, are tmpfs mounted `noexec,nosuid,nodev` with a bounded size that counts against its memory, and `HOME` and every cache lie there, with the Hugging Face hub offline. Every proxy variable, `HTTP_PROXY`, `HTTPS_PROXY`, `FTP_PROXY`, `NO_PROXY` and `ALL_PROXY`, each in upper and lower case, is set empty in every `docker run` and, as a build argument, in every `docker build`, since the Docker CLI fills each one that a command leaves unset from the `proxies` of the user's Docker configuration, which would hand the user's proxy, and any credential in its URL, to every container. It never mounts the home directory, the Docker socket, the clone or a secret: only the files its row names, each bound by itself, read-only, the pinned sources at their pin's layout under `/sources` and the declared outputs of an earlier step under `/inputs/<step>/`, its request directory, read-only, the candidate that the host assembled, read-only, where its row reads it, as its directory for the inspection and the publication, which read every file, and for a run as the files that serve the run's variant alone, each bound by itself under `/candidate/`, and the new, empty directory the host made for its outputs, in mode 2770. Only a row of a GPU image reaches the GPU, through CDI's `nvidia.com/gpu=all`. Every option comes from the step table, `domain/containers/container_steps.py`, which judges each row's limits and outputs against their bounds. Check: `tests/domain/containers/test_container_steps.py` and `tests/adapters/test_docker_engine.py`, on every row, the core's and each recipe's, and the cleaning row of each image.
- **A file that runs code when it loads reaches only the one image declared to read it:** a recipe declares at most one of its images to read the sources that its pins mark `runs_code_when_loaded`, and the recipe is refused when a row of any other image, or of a core image, binds one of them. In that image, the `.nemo` of Parakeet TDT 0.6B v3 is read without its checkpoint ever loading: NeMo reads its configuration alone, with `restore_from(return_config=True)`; the three members of its tokenizer that the configuration names are extracted with `tarfile` and the filter `data`, each found by its name at the archive's root and refused otherwise, into the container's `/tmp`; and the model is built from that configuration, without the sections that name its training data. The checkpoint holds a pickle, which would run its code on load, and the weights come from elsewhere anyway. Check: `tests/domain/contract/test_recipe_contract.py`, on a source that runs code bound in another image or in a core image, and on two images declared to read them; `tests/domain/containers/test_container_steps.py`, on every row; `recipes/parakeet-tdt/tests/test_recipe.py`, which holds the `.nemo` to the export image alone; `recipes/parakeet-tdt/tests/domain/export/test_nemo_configuration.py`, on the members it extracts and the references it refuses.
- **A recipe cannot widen the confinement:** every field of a recipe's contract that reaches Docker or the file system is typed and bounded, and the core judges it when it loads the recipe, before any command runs: the recipe's name and those of its images, steps and variants under their grammar, its images never named like the core's and each on a device, `cpu` or `gpu`, with the extra named after it; each step's entry module a dotted name inside the recipe's own `steps` package, or the core's for a core image, whose file exists as a regular file, checked without importing it; its mounts only pinned files and declared outputs of an earlier step, each bound by itself, never a directory; its outputs under the file-name grammar, with a size bound of at most 8 GiB, `peaks.json` among them; its limits within the step table's bounds; each candidate file under the file-name grammar, without a refused suffix whatever its format, in a format the core knows, `onnx`, `text` or `onnx-external-data`; and the template of its model card, which the host reads, a file name under the same grammar, in the recipe's directory, where it is a regular file, never a link. A recipe is code of the repository, reviewed as any other, and still holds only plain data for the core, so that a mistake in it fails its load rather than widen what a container sees. Check: `tests/domain/contract/test_recipe_contract.py`, on its refusal table; `tests/test_host_main.py`, on the host's check that the card template is a regular file, never a link; `tests/test_recipe_listing.py`, on each recipe's import contracts and Containerfiles.
- **The publication's container holds the token and the network, and runs no code of a model:** the core's `publish` row runs huggingface_hub in the `hub` image, an image that holds no library of a model, on Docker's default bridge, with every other option of a confined container, the token on its standard input, the candidate and its request read-only, and no source, no earlier output and no GPU, which the step table refuses beside the token; the Hugging Face hub is online there alone, `HF_HUB_OFFLINE=0`, with its progress bars off. Its limits, 8 192 MiB, 512 processes, 4 CPUs and 2 048 MiB of `/tmp`, are a hypothesis: they hold the upload of the 2.48 GB external data with hf-xet's chunks in `/tmp`, and the trial publication's peaks settle it. Two risks remain, stated as the lock's are: the default bridge reaches the host's listening services and the local network, besides the Internet; and a dependency of the `hub` image could send the token anywhere. The maintainer's token is fine-grained, with read and write access to the one repository, and revoked once `check-published` passes, which bounds both, and the container holds nothing else of the user's. Neither `step` nor `clean` reaches the row, and the tool never removes a publication's directory, as it never removes a run of `lock`. Check: `tests/domain/containers/test_container_steps.py`, on the row, its environment and its refusals; `tests/adapters/test_docker_engine.py`.
- **The container user is no one's on the host:** a step refuses to run when an account holds 65531, or when a range of `/etc/subuid` or `/etc/subgid`, read strictly, does, since the files its containers leave would then be that account's, or within reach of that account's containers. It is not 65532, the account of mostt's runtimes, which may run on the same machine. Check: `tests/domain/containers/test_account_ranges.py`.
- **Each mount is judged just before the run:** from the work directory down, entry by entry, with `lstat`: no link, each directory the user's, a bound file a regular file of the user's, and a directory where a file is declared refused. An output of an earlier step is judged as the host judges any output: the directory the host made for that step, the user's, holds exactly the names its row declares, and the file is a regular file of the container user's, in mode 0640, within its bound and with a single link, so that a later step reads only what the earlier one declared, and never a link it planted. A row's outputs go into a new directory of its entry in the cache, and a step whose output directory exists is refused; an entry without its record, which an interrupted run leaves, is emptied through the cleaning container and removed before its row runs again, so that no output of an earlier run passes for this one's. Check: `tests/domain/containers/test_container_files.py`, `tests/application/test_run_step.py`, `tests/application/test_run_recipe_step.py` and `tests/application/test_resolve_build.py`.
- **Cleaning goes through a container:** `clean` empties an entry's output directory as 65531, in the image of the step it cleans, a recipe's included, with the core's entry module, with `--network none`, mounting that directory alone, since a directory that a step made inside its outputs is 65531's and the user could not empty it; the host then removes the empty directory, and the request, the log, the record and the candidate's copies it wrote itself. It first judges the entry, the output directory and the request directory as it judges a mount, so that a link in their place stops the cleaning before any container or removal follows it. It keys each entry from the records of the entries before it, never from their outputs, and never judges again nor hashes what it removes, so that a corrupted entry stays removable. Check: `tests/application/test_clean_run.py`.

## Images and outputs

- **A build is reproducible:** its sources are pinned by revision, size and hash; its base images by digest, in `domain/containers/base_images.py`, the Python base and the uv image whose binary the images copy; and its Python packages by hash from `images/environment.lock`, installed with `--frozen --no-build`, with the direct dependencies pinned exactly and `exclude-newer` holding the rest, so that two builds of the same commit read the same bytes. A package published as an sdist alone, which the images' dependency metadata names, is built in a named stage of its image, from the hashes the repository holds, without network: BuildKit fetches its sdist with `ADD --checksum`, at the URL and the hash of its `sdist` entry in `images/environment.lock`, since `pip download` of an sdist would run its `setup.py` with the network; its build requirements, each pinned with `--hash` in its build-requirements file, are downloaded as wheels alone with `--require-hashes`; it is built under `RUN --network=none`, without isolation, with `SOURCE_DATE_EPOCH`; and its wheel, the same to the byte at each build, is checked against the reviewed `built-wheels.sha256` beside the Containerfile, then installed with `--no-deps --no-index --offline` after a main install that leaves it out with `--no-install-package`. The one such package is antlr4-python3-runtime, in the export image of Parakeet TDT, and any other goes to the user. Check: `tests/test_recipe_listing.py`, which accepts no base but those digests, holds each build stage to its accepted forms, its `ADD` to the lock's `sdist` entry and its wheel to its reviewed hash before the install, and `tests/test_lockfiles.py`, which checks both locks: every package from `https://pypi.org/simple`, every distribution under `https://files.pythonhosted.org/` with its SHA-256, and a wheel that installs on Python 3.12 for Linux x86-64, a pure Python wheel tagged for Python 3.12 or an earlier Python 3 included, and a `manylinux` wheel only up to glibc 2.36, bookworm's, so that no image installs a wheel its base cannot load, for every package but the root and those a build stage builds.
- **An image is built from a commit, and runs only at that commit:** `images` refuses a clone with any change, untracked files included, since the host's side runs from the clone and must run the code its images hold; it builds each image from the archive of HEAD's tree, which `git archive` writes, with the user's line endings, global attributes file and umask overridden, and `docker build` reads as its context on its standard input, so that only the files of the tree reach a build, never one that git ignores, such as a `.env`, and labels each image with that tree; a step runs an image by its ID, and refuses it when its label differs from HEAD's tree. `docker build` takes only the arguments the adapter fixes, and no `BUILDKIT_SYNTAX`, so that the built-in frontend reads the Containerfile. A Containerfile holds only the forms its table accepts: first a `FROM` of a pinned base, no parser directive anywhere, the uv binary from its pinned image, the images' manifest, as `pyproject.toml`, and its lock, the sources the image needs at the repository's layout, and last the `ARG` and `LABEL` of the tree, after the heavy layers, which a change of code then reuses. The label then names what the image holds, and a step never runs code that no commit names. The repository's `.git/info/attributes` and the system's gitattributes file can still alter the archive, an accepted risk: they belong to the user or the admin, and no container writes them. Check: `tests/domain/containers/test_provenance.py`, `tests/application/test_build_images.py`, `tests/adapters/test_git_tree.py`, `tests/adapters/test_docker_engine.py` and `tests/test_recipe_listing.py`.
- **Only `lock` resolves the images' lock, and the user reviews its change:** it runs in the `uv` image as 65531, with Docker's default bridge, a read-only root, every capability dropped, no new privileges, its limits and `--rm`, and holds only copies of `images/environment.toml` and `images/environment.lock`, read-only, and its output directory, and no secret. The host judges the new lock as any output, runs the locks' check and the freshness check on it, prints the packages added, removed or changed in version against the committed lock through the filter, and only then writes it to `images/environment.lock`, where the user reviews the change in the diff. Since the images' environment allows a build, a resolution may run the build code of an sdist, and three risks remain: a version that uv tries and drops never reaches the lock, so only the containment holds against it; code that runs during the resolution can change the new lock within what the checks accept, for instance by adding a dependency from PyPI, which the printed change and the review stand against; and the default bridge reaches the host's listening services and the local network, besides the Internet. The freshness check stands in for `uv lock --check`, which no uv on the host can run, since none finds the manifest: the lock records the manifest's `requires-python`, its one environment, its extras and their exact pins, its dependency metadata, its conflicts and its `exclude-newer`. Check: `tests/application/test_resolve_lock.py`, `tests/domain/lock/test_lock_check.py`, `tests/domain/lock/test_lock_freshness.py` and `tests/test_lockfiles.py`.
- **A step's code imports only what it runs:** the entry module of a container step, the core's or a recipe's, imports, even through another module, only the code the step runs and the formats it writes or reads, each with its renderer and its parser: never the step table, the judgment of the files that containers write, the layout of the work directory, the derivation of a run's rows, the recipe contract, the parser of a run's lines, the list of the bench's languages, the card's modules, nor a recipe's `recipe.py`, its variants, its comparisons, the description of its model or its table of onnx-asr's quantizations. What a step shares with the host, such as the paths in its container, the devices, the names and bounds of its outputs and the request of a shard, lives in modules that hold no rule of the host's; the bench's languages reach a step only through its request, held to the form of FLEURS's names, and a variant's files only through the list its request names. The key of a step's outputs covers the step's import closure, so any other module there would rerun the step whenever it changes, and a check of the host's would sit in a container that never runs it. Check: `lint-imports`, from the contract of `pyproject.toml` that forbids these modules to the core's `steps` package and each recipe's, indirect imports included.
- **An output is reused only under the key of what determines it, and judged again before it is read:** each entry of the cache is named by the SHA-256 of a canonical document, `domain/cache/output_keys.py`, of a format number, the row's image, its files at HEAD and the packages of its extra's closure in the images' lock, its code, the bootstrap and the import closure of its entry module in HEAD's tree, its inputs by content, the pins it binds, the SHA-256 of each earlier output and each file of the candidate it reads, its parameters, the row, its request files and the container side of its planned run, and, for a run, the hardware's facts, read strictly from `/proc`; the host's paths, the image's ID and the user's ids stay out. A key that missed a determinant would let a stale output pass for a new one, so the document takes the whole row and every option of its run rather than a chosen part. An entry is reused only with its record, the host's own file, read strictly, whose key and row match, and only once its outputs pass the judgment of a later step's mount and hash again to the record's digests; it is then read through the same parsers and judgments as an output just written, and a reused candidate through the checks of its copy, so that a report that today's parser refuses, or a copy that today's checks refuse, is refused whatever check it passed when it was made. A refused entry names `clean <step>`, and `clean` removes it without judging it. Check: `tests/domain/cache/test_output_keys.py`, `tests/domain/cache/test_import_closure.py`, `tests/domain/cache/test_hardware_facts.py`, `tests/domain/lock/test_extra_closure.py`, `tests/domain/cache/test_output_records.py`, `tests/application/test_resolve_build.py` and `recipes/parakeet-tdt/tests/test_recipe_keys.py`.
- **A file leaves the work directory only once it is verified:** it passes the checks of its format and the comparison of its outputs with the reference framework's, and its accuracy is measured on FLEURS, before it becomes a candidate for publication. Only the user publishes a candidate: `publish` refuses to go on unless its standard input is a terminal, before it opens the work directory, prepares the publication as `card` does, refuses a card that differs from the one written for review, or a missing one, shows the repository and each file with its size and its SHA-256, asks the user to type the repository again and stops on a difference, reads the token with echo off, judges the inspected copies again, and holds the container's report to the request, so that the bytes the container read and committed are those the verification accepted and the card is the one reviewed; the step refuses before it commits when a file reads otherwise, and refuses a repository that holds any file but the Hub's `.gitattributes` and the build's own. `verify` first reads the report of `inspect` through the judgment of its outputs, judges every file of the candidate as the host's own copy, in mode 0444, with a single link and within the bound of its origin, and runs the inspection's rules again on them, so that no candidate that its inspection refused, never inspected or changed since is measured; it then hashes each file of the candidate through the descriptor of the judged candidate directory, opened with `O_DIRECTORY | O_NOFOLLOW`, each file relative to it with `O_NOFOLLOW | O_NONBLOCK`, judges that descriptor's `fstat` facts as the host's own copy again, and records each file's size and SHA-256 in `verification.json`, so that the bytes it accepted are on record; and the model card is rendered only from a verification that `card` runs again, from a clean clone, and that accepts the build, so that no card vouches for outputs that changed or for code that no commit names; it reads every output it measures through the judgment of a later step's mount, and reads the index of the bench, a pinned source, only once its size and its SHA-256 match its pin again, so that neither a container nor a changed file of the work directory chooses what the build is measured against.
