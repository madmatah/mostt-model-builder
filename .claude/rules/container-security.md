# Container security

A build loads the code of the models' frameworks, such as NeMo, torch and Transformers, and files that run code when they load, such as a pickle or a `.nemo` checkpoint. That code is untrusted: it runs only in containers, and the host treats what they write as hostile. These rules grow with the build's code.

## The host

- **The host runs on its own Python and the standard library, isolated:** the host's side of the build runs under `-I -S -B` and imports only the standard library and the project's own packages, never a library of the steps, such as torch, NeMo, Transformers, onnx or ONNX Runtime. `-I` ignores the environment's Python variables, the user's site directory and the current directory, `-S` leaves the site packages out, and `-B` writes no bytecode into the clone, so that nothing installed on the host, and nothing planted beside the code, runs with the user's rights. The one place that changes `sys.path` is the bootstrap, `src/mostt_model_builder/bootstrap.py`, which the launcher, `model-build.sh`, and every step run by path: it appends the project's `src` and each recipe's, and only a real directory whose name follows the recipe grammar, then runs the entry module it is given. It imports nothing of the packages, since it runs before they are on the path. Check: `tests/test_mostt_model_builder.py` imports the command line under `-I -S -B` and refuses any module from outside the standard library and the package; `tests/test_model_build_launcher.py` checks that the launcher runs the bootstrap under `-I -S -B`; `tests/test_bootstrap.py` checks the paths the bootstrap appends and the entry modules it refuses; `lint-imports` keeps the bootstrap's imports out of the packages.
- **A container step's Python runs under `-I -B`:** the image's own Python, which keeps its site for the libraries the image installed, and nothing from the environment or the working directory, so that a step runs the same code at every build. The host starts it itself, with `--entrypoint` naming the image's Python, `/opt/venv/bin/python` in an image with an environment and the base's `/usr/local/bin/python3.12` in one without, then `-I -B`, the image's copy of the bootstrap and the row's entry module, and never relies on an image's own entry point. Check: `tests/domain/containers/test_container_steps.py` and `tests/adapters/test_docker_engine.py`, on every row.
- **Root is refused:** the bootstrap's first act, before it reads anything, is to exit with status 77 when any of the real, effective or saved user or group ids of its process is 0. A build as root would leave files in the work directory that the user cannot remove, and would give any mistake of the launcher the whole machine. Check: `tests/test_bootstrap.py`, on each of the six ids.
- **uv never builds a package on the host:** `no-build = true` in the host's `[tool.uv]`, in `pyproject.toml` at the root, so that every install takes a wheel by its hash and no package's build code, such as a `setup.py`, runs outside a container. Check: `tests/test_project_manifests.py` holds the host's `[tool.uv]` to exactly `package = false` and `no-build = true`; `tests/test_lockfiles.py` runs the locks' check on `uv.lock`, which refuses a package without a wheel that installs on Python 3.12 for Linux x86-64.
- **uv never runs on the images' environment on the host:** `images/pyproject.toml` allows a build, `no-build = false`, since one of its packages is published as an sdist alone, so a resolution or an install there would run that package's build code with the user's rights. Its `required-version`, the uv of the `uv` image, makes every other version of uv exit with an error in that project, and keeps the lock's layout tied to the images' uv. A uv of the same version, which the host's and CI's are when all follow one release, passes it, and against it no command, gate step, CI step or hook runs uv in `images/`, since the gate reads its lock as text and only `./model-build.sh lock` resolves it, in a container, and no one runs uv there by hand either. Check: `tests/test_project_manifests.py` holds `required-version` to the uv version of `domain/containers/base_images.py`; review, the rest.
- **The host reaches the network only to fetch the sources, resolve the images' lock and build the images:** `fetch` runs curl on the host, `lock` runs its container on Docker's default bridge, and `docker build` has Docker's network; every other step runs with `--network none`, so that no code of a model and no reader of its files can reach the outside world. Check: `tests/domain/containers/test_container_steps.py` and `tests/adapters/test_docker_engine.py`, on every row.
- **A source is fetched over HTTPS alone, and kept only once it matches its pin:** each source is pinned in a `sources.toml`, the core's at the root of the clone, by its Hugging Face repository, a revision that is a full 40-digit commit, its path, its size and its SHA-256, and its URL is built only from a pin that the host's parser accepted. curl takes `--disable` first, so that no configuration file of the user's adds an option, then HTTPS alone, redirects included, at TLS 1.2 or later, no globbing, a size bounded by the pin, and `--` before the URL. A download lands in a partial file, which takes its name in the work directory only once its size and its SHA-256 match the pin, and is removed otherwise; a fetched file is left read-only, and is checked again at every fetch. A branch or a tag would let the files change under the same pin, and a file kept unchecked would reach every container that reads it. Check: `tests/domain/sources/test_source_pins.py`, `tests/application/test_fetch_sources.py` and `tests/adapters/test_curl_downloader.py`.
- **A source's name never marks code, a pickle or an archive, unless its pin says it runs code:** the file name of a pin is refused when any of its suffixes, whatever its case, marks code, a pickle, an archive or a format that runs code when it loads, such as `.pt`, `.bin`, `.nemo`, `.py`, `.zip` or `.tgz`: the suffixes that the published files refuse, without `.tar` and `.gz`, since FLEURS ships its audio as `.tar.gz` archives that a container reads member by member. Only a pin that says `runs_code_when_loaded = true`, a boolean and nothing else, may name such a file, and that mark then follows the file to every row that binds it ([Confinement](#confinement)). A file that runs code when it loads must never reach a container that was not built to read it, so it is never fetched unmarked. Check: `tests/domain/sources/test_source_pins.py`, on each refused suffix, on the list of them and on the mark; `tests/test_recipe_listing.py`, which holds every `sources.toml` of the repository to exactly one marked file, the `.nemo` of Parakeet TDT 0.6B v3.
- **The work directory is the user's own, outside the home directory and the clone:** it is given by `--work`, never by a default, and must match `/[A-Za-z0-9._/-]+`, be canonical, exist as a directory and not a link, belong to the user, and have the mode 0700 exactly. It is neither the home directory, nor under it, nor around it, where the home directory is both `$HOME` and the account's home, each canonical, and a missing or relative `$HOME` is refused; and it lies neither under the clone nor around it. Containers write into it and the host binds its files into them, so a work directory that held the home directory or the clone would bring the user's files, secrets or code within their reach, and one that another user could write into would let that user swap a file between its check and its use. The grammar is checked before the path is read, and keeps it free of the characters that Docker's options and a shell read as syntax. Check: `tests/domain/containers/test_work_directory.py` and `tests/application/test_open_work_directory.py`.
- **What a container prints or writes is data, never an instruction:** the host takes no command, path or decision from it beyond what a strict, bounded parser of its own accepts, one parser per kind of file, each with its refusal tests: `domain/containers/step_peaks.py` for every `peaks.json`, `domain/bench/fleurs_check_report.py` for the report of `fleurs-check`, `domain/lock/lock_check.py` and `lock_freshness.py` for the lock that `lock` writes, `domain/acceptance/parity_reports.py` for every parity report, such as the export's against NeMo, which must name the parity the recipe declares, `domain/onnx/conversion_report.py` for the report of the conversions, which must describe the conversions the host asked for, in their order, `domain/onnx/inspection_report.py` for the inspection's report of the candidate's graphs, `domain/onnx/node_placement.py` for the placement summary of a run on the GPU, and `domain/bench/hypotheses.py` for the lines of every run, which reach the core only through the run's reader, a pure function of its recipe, such as `recipes/parakeet-tdt/src/mostt_recipe_parakeet_tdt/domain/transcripts/run_readers.py` with `token_rendering.py` and `vocabulary.py`. Each parser of JSON refuses a document nested deeper than 32 levels before it decodes it, in a single pass over its characters, since json's decoder recurses once per level and a scan whose cost grew faster than the text would let a container stall the host. An output that no parser of the host reads, such as the name lists of `describe` or the files of the export, is judged as any output, and the host takes nothing from it but its size, which it reports, or, for a file of the candidate, its copy. The name lists that a recipe's tests read from their committed copies go through a strict parser of the recipe's, `recipes/parakeet-tdt/src/mostt_recipe_parakeet_tdt/domain/export/tensor_fixtures.py`, which holds their names, types and shapes to printable ASCII, so that no character a reader cannot see enters the repository through them. A step leaves regular files only, at the top of its output directory, under the names its row declares, each in mode 0640 and within its size bound. The host opens that directory with `O_DIRECTORY | O_NOFOLLOW` once it has judged it, and each file relative to it with `O_NOFOLLOW | O_NONBLOCK`; it judges the file by `fstat`, a regular file owned by 65531, in mode 0640 exactly, without setuid or setgid, within its bound and with a single link, reads through that descriptor only the files that one of its parsers reads, judging every other by its facts alone, and refuses an undeclared entry, so that no link and no swapped file leads it to read what a container chose, and no large output, such as the external data of a model, enters the host's memory only to be measured. What a container prints goes to its log, outside every output directory, through a filter that turns every byte outside printable ASCII, the tab and the line feed into `?`, capped at 16 MiB and drained beyond; on a failure, the terminal shows only the log's last 8 KiB, and the output of `docker build` takes the same path. A container value quoted in a message is shown through `ascii()`. The output can then neither forge the terminal's display nor fill the disk. Check: `tests/domain/containers/test_container_files.py`, `tests/application/test_run_step.py`, `tests/application/test_run_recipe_step.py`, `tests/application/test_convert_variants.py`, `tests/adapters/test_work_files.py`, `tests/domain/containers/test_printable_output.py`, `tests/domain/json_documents/test_json_depth.py` and the refusal tests of each parser, `recipes/parakeet-tdt/tests/domain/export/test_tensor_fixtures.py` and the recipe's tests of its readers included.
- **The candidate is the host's own copy, checked whole before any run reads it:** the host copies each file the recipe names from the declared output of its step, through the descriptor of the step's judged directory, into a new file in mode 0444 in a new candidate directory, never a link, and writes the contents the recipe gives itself; as each file streams by, it refuses one whose first 512 bytes carry the signature of code, a pickle or an archive, `domain/formats/file_signatures.py`, whatever its format, and one that fails its format's structural check, `domain/formats/file_formats.py`. The inspection then reads every `onnx` file in a container, every node and every tensor of its main graph, of each subgraph at any depth and of each function, `domain/onnx/model_graphs.py`, and the host refuses a node of an unknown domain or a call to a function the model does not define, a node that holds `metadata_props`, which may name paths of the container, a training graph, which no runtime of the candidate runs, a sparse initializer in any graph, whose weights no rule of the products judges, a tensor outside the external data the contract gives, a constant weight of the conversions' input that is not a plain 2-D initializer, and in the output of the conversion to 8-bit blocks a product of a constant weight left unquantized or a count of `MatMulNBits` other than its recipe declares, each rule following where a file comes from and never its name, `domain/onnx/graph_rules.py`, and external data that a tensor overruns, overlaps, leaves a gap or padding in, or that another `onnx` file names, `domain/formats/external_data.py`. Every row that binds the candidate, each shard of a run included, reads the inspection's report again and judges its rules and every copy of the candidate before its container starts, so that a run never reads a candidate that its inspection refused, never inspected, or that changed since; and the assembly refuses to start while the outputs of an earlier inspection remain. A file of the candidate then holds only what its recipe declared, in a form that loads no code, and no container can change it once checked. Check: `tests/application/test_assemble_candidate.py`, `tests/application/test_run_recipe_step.py`, `tests/domain/onnx/test_model_graphs.py`, `tests/domain/containers/test_container_files.py`, `tests/domain/formats/test_file_signatures.py`, `tests/domain/formats/test_file_formats.py`, `tests/domain/onnx/test_graph_rules.py` and `tests/domain/formats/test_external_data.py`.

## Confinement

- **The code of a model runs only in a container:** the libraries of the steps, and any file that runs code when it loads, are loaded nowhere else. Nothing is installed on the host for them.
- **A container that loads that code has no network, no privilege and none of the host's secrets:** `--network none`, a read-only root, `--cap-drop ALL`, `--security-opt no-new-privileges`, `--ipc none`, `--log-driver none`, `--ulimit core=0`, `--rm` and `--pull never`; the unprivileged user 65531 in the user's group; and limits on its memory, with its swap at the same value, its processes and its CPUs, each a positive integer within its bounds, since Docker reads 0 or -1 as no limit. Its `/tmp`, and its `/scratch` where its row asks for one, are tmpfs mounted `noexec,nosuid,nodev` with a bounded size that counts against its memory, and `HOME` and every cache lie there, with the Hugging Face hub offline. Every proxy variable, `HTTP_PROXY`, `HTTPS_PROXY`, `FTP_PROXY`, `NO_PROXY` and `ALL_PROXY`, each in upper and lower case, is set empty in every `docker run` and, as a build argument, in every `docker build`, since the Docker CLI fills each one that a command leaves unset from the `proxies` of the user's Docker configuration, which would hand the user's proxy, and any credential in its URL, to every container. It never mounts the home directory, the Docker socket, the clone or a secret: only the files its row names, each bound by itself, read-only, the pinned sources at their pin's layout under `/sources` and the declared outputs of an earlier step under `/inputs/<step>/`, its request directory, read-only, the candidate that the host assembled, read-only, where its row reads it, and the new, empty directory the host made for its outputs, in mode 2770. Only a row of a GPU image reaches the GPU, through CDI's `nvidia.com/gpu=all`. Every option comes from the step table, `domain/containers/container_steps.py`, which judges each row's limits and outputs against their bounds. Check: `tests/domain/containers/test_container_steps.py` and `tests/adapters/test_docker_engine.py`, on every row, the core's and each recipe's, and the cleaning row of each image.
- **A file that runs code when it loads reaches only the one image declared to read it:** a recipe declares at most one of its images to read the sources that its pins mark `runs_code_when_loaded`, and the recipe is refused when a row of any other image, or of a core image, binds one of them. In that image, the `.nemo` of Parakeet TDT 0.6B v3 is read without its checkpoint ever loading: NeMo reads its configuration alone, with `restore_from(return_config=True)`; the three members of its tokenizer that the configuration names are extracted with `tarfile` and the filter `data`, each found by its name at the archive's root and refused otherwise, into the container's `/tmp`; and the model is built from that configuration, without the sections that name its training data. The checkpoint holds a pickle, which would run its code on load, and the weights come from elsewhere anyway. Check: `tests/domain/contract/test_recipe_contract.py`, on a source that runs code bound in another image or in a core image, and on two images declared to read them; `tests/domain/containers/test_container_steps.py`, on every row; `recipes/parakeet-tdt/tests/test_recipe.py`, which holds the `.nemo` to the export image alone; `recipes/parakeet-tdt/tests/domain/export/test_nemo_configuration.py`, on the members it extracts and the references it refuses.
- **A recipe cannot widen the confinement:** every field of a recipe's contract that reaches Docker or the file system is typed and bounded, and the core judges it when it loads the recipe, before any command runs: the recipe's name and those of its images, steps and variants under their grammar, its images never named like the core's and each on a device, `cpu` or `gpu`, with the extra named after it; each step's entry module a dotted name inside the recipe's own `steps` package, or the core's for a core image, whose file exists as a regular file, checked without importing it; its mounts only pinned files and declared outputs of an earlier step, each bound by itself, never a directory; its outputs under the file-name grammar, with a size bound of at most 8 GiB, `peaks.json` among them; its limits within the step table's bounds; and each candidate file under the file-name grammar, without a refused suffix whatever its format, in a format the core knows, `onnx`, `text` or `onnx-external-data`. A recipe is code of the repository, reviewed as any other, and still holds only plain data for the core, so that a mistake in it fails its load rather than widen what a container sees. Check: `tests/domain/contract/test_recipe_contract.py`, on its refusal table; `tests/test_recipe_listing.py`, on each recipe's import contracts and Containerfiles.
- **The container user is no one's on the host:** a step refuses to run when an account holds 65531, or when a range of `/etc/subuid` or `/etc/subgid`, read strictly, does, since the files its containers leave would then be that account's, or within reach of that account's containers. It is not 65532, the account of mostt's runtimes, which may run on the same machine. Check: `tests/domain/containers/test_account_ranges.py`.
- **Each mount is judged just before the run:** from the work directory down, entry by entry, with `lstat`: no link, each directory the user's, a bound file a regular file of the user's, and a directory where a file is declared refused. An output of an earlier step is judged as the host judges any output: the directory the host made for that step, the user's, holds exactly the names its row declares, and the file is a regular file of the container user's, in mode 0640, within its bound and with a single link, so that a later step reads only what the earlier one declared, and never a link it planted. A step whose output directory exists is refused, and the message names `clean`, so that no output of an earlier run passes for this one's. Check: `tests/domain/containers/test_container_files.py`, `tests/application/test_run_step.py` and `tests/application/test_run_recipe_step.py`.
- **Cleaning goes through a container:** `clean` empties a step's output directory as 65531, in the image of the step it cleans, a recipe's included, with the core's entry module, with `--network none`, mounting that directory alone, since a directory that a step made inside its outputs is 65531's and the user could not empty it; the host then removes the empty directory, and the request and the log it wrote itself. It first judges the output directory, the request directory and the directory of the log as it judges a mount, so that a link in their place stops the cleaning before any container or removal follows it. Check: `tests/application/test_clean_run.py`.

## Images and outputs

- **A build is reproducible:** its sources are pinned by revision, size and hash; its base images by digest, in `domain/containers/base_images.py`, the Python base and the uv image whose binary the images copy; and its Python packages by hash from `images/uv.lock`, installed with `--frozen --no-build`, with the direct dependencies pinned exactly and `exclude-newer` holding the rest, so that two builds of the same commit read the same bytes. A package published as an sdist alone, which the images' dependency metadata names, is built in a named stage of its image, from the hashes the repository holds, without network: BuildKit fetches its sdist with `ADD --checksum`, at the URL and the hash of its `sdist` entry in `images/uv.lock`, since `pip download` of an sdist would run its `setup.py` with the network; its build requirements, each pinned with `--hash` in its build-requirements file, are downloaded as wheels alone with `--require-hashes`; it is built under `RUN --network=none`, without isolation, with `SOURCE_DATE_EPOCH`; and its wheel, the same to the byte at each build, is checked against the reviewed `built-wheels.sha256` beside the Containerfile, then installed with `--no-deps --no-index --offline` after a main install that leaves it out with `--no-install-package`. The one such package is antlr4-python3-runtime, in the export image of Parakeet TDT, and any other goes to the user. Check: `tests/test_recipe_listing.py`, which accepts no base but those digests, holds each build stage to its accepted forms, its `ADD` to the lock's `sdist` entry and its wheel to its reviewed hash before the install, and `tests/test_lockfiles.py`, which checks both locks: every package from `https://pypi.org/simple`, every distribution under `https://files.pythonhosted.org/` with its SHA-256, and a wheel that installs on Python 3.12 for Linux x86-64, a pure Python wheel tagged for Python 3.12 or an earlier Python 3 included, and a `manylinux` wheel only up to glibc 2.36, bookworm's, so that no image installs a wheel its base cannot load, for every package but the root and those a build stage builds.
- **An image is built from a commit, and runs only at that commit:** `images` builds from a clone clean of every change, untracked files included, with the repository root as its context and an allow-list dockerignore beside each Containerfile; it labels each image with the git tree of HEAD, a step runs an image by its ID, and refuses it when its label differs from HEAD's tree. `docker build` takes only the arguments the adapter fixes, and no `BUILDKIT_SYNTAX`, so that the built-in frontend reads the Containerfile. A Containerfile holds only the forms its table accepts: first a `FROM` of a pinned base, no parser directive anywhere, the uv binary from its pinned image, the sources the image needs at the repository's layout, and last the `ARG` and `LABEL` of the tree, after the heavy layers, which a change of code then reuses. The label then names what the image holds, and a step never runs code that no commit names. Check: `tests/domain/containers/test_provenance.py`, `tests/application/test_build_images.py`, `tests/adapters/test_git_tree.py`, `tests/adapters/test_docker_engine.py` and `tests/test_recipe_listing.py`.
- **Only `lock` resolves the images' lock, and the user reviews its change:** it runs in the `uv` image as 65531, with Docker's default bridge, a read-only root, every capability dropped, no new privileges, its limits and `--rm`, and holds only copies of `images/pyproject.toml` and `images/uv.lock`, read-only, and its output directory, and no secret. The host judges the new lock as any output, runs the locks' check and the freshness check on it, prints the packages added, removed or changed in version against the committed lock through the filter, and only then writes it to `images/uv.lock`, where the user reviews the change in the diff. Since the images' environment allows a build, a resolution may run the build code of an sdist, and four risks remain: a version that uv tries and drops never reaches the lock, so only the containment holds against it; code that runs during the resolution can change the new lock within what the checks accept, for instance by adding a dependency from PyPI, which the printed change and the review stand against; the default bridge reaches the host's listening services and the local network, besides the Internet; and a uv at exactly the images' `required-version`, such as the host's whenever it is at that version, run by hand in `images/`, would build on the host. The freshness check stands in for `uv lock --check`, which no host command may run there: the lock records the manifest's `requires-python`, its one environment, its extras and their exact pins, its dependency metadata, its conflicts and its `exclude-newer`. Check: `tests/application/test_resolve_lock.py`, `tests/domain/lock/test_lock_check.py`, `tests/domain/lock/test_lock_freshness.py` and `tests/test_lockfiles.py`.
- **A file leaves the work directory only once it is verified:** it passes the checks of its format and the comparison of its outputs with the reference framework's, and its accuracy is measured on FLEURS, before it becomes a candidate for publication. Only the user publishes a candidate.
