# Develop

`CLAUDE.md` > Workflow holds the rules this procedure applies. Below, `<base>` is `origin/main`, or the unmerged branch the work is stacked on. Write each file whose text you write, such as the findings that the fixes answer or a commit message, with the Write tool, never through a shell: in a heredoc, or in `git commit -m "…"`, the backquoted text that findings, plans and messages quote runs as commands. A command's output goes to its file by redirection. Give git a message from a file in a directory that `mktemp -d` creates outside the worktree, with `git commit -F <file>`. A session that did not start in the branch's worktree reads `.claude/rules/configuration.md` > Claude Code automation, "An agent given a worktree works only there", and runs each command below on the branch as it says.

## Start a branch

1. Run `git fetch origin`, then `git worktree add --no-track -b <type>/<topic> .claude/worktrees/<name> origin/main`, with a type from `CLAUDE.md` > Workflow, "Commits".
2. `claude --worktree <name>` names its branch `worktree-<name>`: rename it with `git branch -m <type>/<topic>`.
3. Install the dependencies of a worktree you add during a session, as `CLAUDE.md` > Workflow, "Dependencies" says.

## Plan the work

Plan the work as `CLAUDE.md` > Workflow, "Plan before writing code" says, and revise the plan the same way when the code or a review shows it wrong.

When the work calls for a mock, as `CLAUDE.md` > Workflow, "A mock comes before the plan of an output a person reads" says, write it before the planner first runs, with the Write tool, beside the plan, at the plan's path with `.mock.md` in place of `.md`: Markdown or text, a screen sketched in text, with realistic, invented values, and one sample for each case that changes what the reader sees. Show it to the user in your reply, and change it as they ask until they approve it; when the user does not follow the work, go on from it, and say in your final report, and in the Proposal of the pull request, which shows it, that it is not approved. The mock is part of the goal: wherever a step gives the goal, give the mock's path too, and say whether the user approved it, and commit it wherever the plan is committed. A change of that output, whoever calls for it, goes to the user, as a change of the goal does, or, when the user does not follow the work, is yours to make, marked as not approved, and named in your final report and in the Proposal.

1. Spawn the `planner` agent with its brief: the worktree and its base, the path of the plan, the goal and where it comes from, the constraints and the decisions you know, and, when your instructions keep the project-management material somewhere, its path and that of its decision log. The plan goes where your instructions keep the plan of a branch; without such instructions, to a file outside the repository, whose path you give the user. Never in the repository: `CLAUDE.md` > Project management. For a revision, add what showed the plan wrong, such as the findings of a review, and the commits of the branch with their files, from `git log --format='%h %s' --name-only <base>..HEAD`. The planner writes the plan itself and returns a short report: a summary, what changed in a revision, its open questions and its answers to the critic. Read the plan only where the report leaves you a question: you carry every file you read for the rest of the work.
2. When the planner reports that it could not write the plan, stop, and tell the user, or, when the user does not follow the work, say in your final report, the path that the planner needs leave to write, and any open points of the critic.
3. Spawn the `plan-critic` agent with the worktree, its base, the goal, the constraints, the decisions and the user's answers you know, and the path of the plan, and, for a revision, what showed the plan wrong and the commits of the branch, as the planner got them. Resume the planner with the critic's blocking and should-fix points, rather than spawning a new one that would read the code again, then resume the critic with the planner's answers: it checks the whole plan again. Go on until the critic says `ready`. After three rounds, ask the user about what remains, or, when the user does not follow the work, stop and give the path of the plan and its open points in your final report.
4. Once the critic says `ready`, commit the plan as your instructions say.
5. When the user follows the work, give them the path of the plan, and the summary and the open questions of the planner's last report, and wait for their approval. Resume the planner with a change they ask for, then the critic with that change, as the user's answer, as for the critic's points, until the critic says `ready` again, and commit the plan once more. Otherwise, take the answer that the plan recommends to each open question, and name it in the pull request.

## Write the code

Write the code from the plan, or give it to an agent on Opus at `high`, as `.claude/rules/configuration.md` > Claude Code automation says, with the worktree, its base, the path of the plan and that of its mock, when it has one, and the bound that `.claude/rules/configuration.md` > Claude Code automation, "An agent given a worktree works only there" sets: it reads that rule before its first command, then the plan and its mock, and writes each commit message as `.claude/skills/develop/SKILL.md` > Develop says. When the plan proves wrong, stop, and revise it as [Plan the work](#plan-the-work) says. If an agent was writing the code, commit or drop its work in progress, as the revised plan says, then give the rest to a new agent, with the revised plan and the commits so far: the one that stopped carries a context that only grows.

## Stack on an unmerged branch

- **A branch may start from another unmerged branch whose work it needs:** give that branch instead of `origin/main` to `git worktree add`. Until it is merged, it is `<base>`: review against it, as [Review](#review) says, autosquash onto it, and open the pull request against it, naming it in the Proposal.
- **Whenever the base is rewritten,** by its review fixes or by its merge, move only your own commits: `git rebase --onto <new base> $(git merge-base --fork-point <branch> HEAD)`. The new base is the branch itself, or `origin/main` once it is merged; the old copies of its commits would conflict with the new ones. Once the base is merged, retarget the pull request to `main`, as `.claude/skills/pull-request/SKILL.md` > Update the body says.
- **The owner of a base keeps it until the branches built on it have moved.** Each of those branches is moved by its own owner.

## Shape the history

1. Before pushing, rewrite the branch into atomic commits, as `CLAUDE.md` > Workflow, "Commits" and "A commit message says why" ask, and write each message with the `writing-commits` skill. Interactive editors are unavailable: fold a change into its commit with `git commit --fixup=<commit>`, then `GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <base>`.
2. Check every commit, as `CLAUDE.md` > Workflow, "Commits" and "Run each check once, at its level" ask: each one on what it touches, with `git rebase --exec 'scripts/check-commit.sh' <base>`. The CI runs the whole gate; run `scripts/check.sh` here only where "Run each check once, at its level" says. When a commit fails, take its hash from `git rev-parse --short HEAD`, run `git rebase --abort`, commit the fix with `git commit --fixup=<that commit>`, written by you or, once the branch is under review, by a new `fixer` agent with the brief that [Review](#review) gives it and the failure as its finding, whose fix the pull request names among the fixes that no expert checked. Fold it with `GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <base>`, and check again.

## Review

1. Run `/expert-review <branch>`, or `/expert-review <base>...<branch>` when it is stacked, naming the branch rather than `HEAD`: the review runs in the session's directory, whose `HEAD`, in the main checkout, is another branch. Run one review at a time in a session: one started while another runs waits in the foreground, where it can hand back before its agents answer. The review runs in the background, and its report reaches you as a message; under `claude -p`, or with `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` set, it runs in the foreground, and its report is the result of the call. Wait for it before you settle anything. A report that says its triage or an expert still runs was handed back too soon, as the step on a review handed back too soon says. Claude Code loads the skills and agents of the session's directory, not the branch's: a session that did not start in the branch's worktree reviews and fixes it with its own definitions, and one started there with the branch's own. When the branch changes the skills or agents that review or fix it, the pull request names the definitions that reviewed it, and says when they are not the branch's.
2. Settle each finding as `CLAUDE.md` > Workflow, "Review before pushing" says. A finding that needs a change of design, or of the output that the mock settles, goes back to the plan, with all the findings of the review: revise the plan of the branch, as [Plan the work](#plan-the-work) says, give the change to a new agent, as [Write the code](#write-the-code) says, shape the history again, as [Shape the history](#shape-the-history) says, and review the whole branch once again, as the first review does. Otherwise, give the findings to fix to a new `fixer` agent, with its brief: the worktree and its base, the purpose of the branch, each verified finding with its severity, and the commit each fix belongs to. It fixes the blocking findings first, and commits each fix as a `fixup!` commit, or as an `amend!` commit for a commit message, as [Fold review fixes](#fold-review-fixes) shows, and leaves no commit that fails its check.
3. Before you fold them, check the fixes of blocking findings, when the fixer fixed any: write the blocking findings that the fixer fixed, as the review reported them, to a file in a directory that `mktemp -d` creates outside the worktree, and run `/expert-review <the commit before the first fix>...<end> --fixes <file>`, where `<end>` is, among the commits that the fixer's report gives for blocking findings, the one that `git log --format=%h <base>..<branch>` lists first. A fix of a should-fix or nit finding that lies inside that range is checked with them. Remove the directory once you have settled each finding of its report, as the next step says, unless the check handed back too soon. The check starts no further round.
4. When anything remains, give it to a new `fixer` agent, with the same brief, and, for a finding whose fix failed its check, that check's output: each defect the check found, each blocking finding it reports `open`, and each finding that the first fixer left `not fixed` after undoing a commit whose check failed, when the finding is blocking or the failure came from an earlier fix. Its fixes are not checked. A finding that a fixer leaves goes back to the plan when its fix needs a change of design, as a finding of the review does, and is answered in the pull request otherwise. Name in the pull request every fix that no expert checked: the fixes of should-fix and nit findings outside the checked range, and this fixer's. Then fold them.
5. If the review hands back a report that says its triage or an expert still runs, or an answer of its triage or of an expert reaches you rather than the review, the review handed back too soon: set its report aside and act on none of it. Stop, and tell the user, or, when the user does not follow the work, say in your final report: the answers that reached you, what you already started from that report, such as a fixer and its commits, in a check of fixes the path of its `--fixes` file, and the detached worktrees outside the repository that `git worktree list` shows, which this review or another one still running may use. Remove none of them and run no review again: the review's agents may still be running, and only the user decides what happens next.

## Push the branch and watch its CI

1. Push the branch: `git push -u origin HEAD` the first time.
2. Open the pull request as the `pull-request` skill > Open the pull request says.
3. Make sure CI (`scripts/check.sh` on GitHub Actions) passes on it: `gh pr checks <number> --watch`. The `link` of a failed check, from `gh pr checks <number> --json name,bucket,link`, holds its run id, as `/actions/runs/<run-id>/`. A failure of the runner or the network, not of the gate, is run again with `gh run rerun <run-id> --failed`. A failure of the gate goes to a new `fixer` agent as a finding that names the failing step, the command that runs it and its output, from `gh run view <run-id> --log-failed`, with the brief that [Review](#review) gives it, and the commit it belongs to, which you find from the files of the failing step, by meaning, as [Fold review fixes](#fold-review-fixes) finds the target of a leftover. Fold its fix as [Fold review fixes](#fold-review-fixes) says, which checks the commits again, pushes and updates the body: name the fix there among the fixes that no expert checked. Then watch the CI again. When the fixer fixes nothing, or the same step fails a second time, stop and tell the user, or, when the user does not follow the work, say in your final report, with the step and its log.

## Fold review fixes

1. Commit each fix with `git commit --fixup=<commit>`, naming the commit it belongs to. A fix to the message of a commit goes in an `amend!` commit, since a `fixup!` commit keeps the message of its target: in a directory that `mktemp -d` creates outside the worktree, write, with the Write tool, a file whose first line is `amend! ` followed by the header of the commit, whole, as `git log -1 --format=%s <commit>` prints it, since autosquash matches that line, then a blank line and the whole new message; run `GIT_EDITOR="cp <file>" git commit --fixup=reword:<commit>`, or `--fixup=amend:<commit>` to fold the staged changes with it, and remove the directory. Neither `-m` nor `-F` combines with these forms.
2. Run `GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <base>`. Git before 2.44 ignores `--autosquash` without `-i`, and the `-i` form works with every version.
3. Check that `git log --format='%h %s' <base>..HEAD` lists no `fixup!`, `amend!` or `squash!` commit. One that is left names, by its first line, no whole header of `<base>..HEAD`: find the commit it fixes by meaning, in that list or, on a stacked branch, in `git log --format='%h %s' origin/main..<base>`. Take the leftovers one at a time, each from a fresh listing and with its own directory that `mktemp -d` creates outside the worktree, since each drop rewrites the commits after it. `<leftover>`, and `<that commit>` below, are only the abbreviated hash that the listing prints, nothing else of its line, since the rest is a commit's message. For each `<leftover>`:
   - **save it:** its change with `git diff --binary <leftover>^ <leftover> > "<dir>/fix.patch"`, since `git apply` cannot apply a binary file from a plain diff, and the message of an `amend!` or `squash!` commit with `git log -1 --format=%B <leftover> > "<dir>/message"`;
   - **drop it:** `git rebase --onto <leftover>^ <leftover>`;
   - **when it fixes a commit of `<base>..HEAD`,** commit the fix again: `git apply --3way "<dir>/fix.patch"`, skipped when the patch is empty, as a reworded message leaves it, then `git commit --fixup=<that commit>`, or, for an `amend!` commit, the `amend!` form above, from the saved message under a corrected first line, and for a `squash!` commit the same form, from the message of that commit, `git log -1 --format=%B <that commit>`, followed by the saved message without its first line; fold again, and remove `<dir>`;
   - **when it fixes a commit of the branch this one is stacked on,** the fix belongs to that branch: its owner commits it there as above and folds it, then this branch moves, as [Stack on an unmerged branch](#stack-on-an-unmerged-branch) says. When another session owns that branch, keep `<dir>`, put the finding and the paths of `fix.patch`, and of `message` when one was saved, in your final report, for the coordinating session to pass on to that owner, and name the finding in the pull request. A check of this branch that fails for want of that fix waits for the move;
   - **when a step conflicts or fails,** such as `git apply --3way` that exits with an error and no conflict when the file it patches was deleted, undo it and keep `<dir>`: `git rebase --abort` when the drop stops, which leaves the leftover on the branch, or when the fold stops, which leaves the fix as a commit; `git reset --merge` when `git apply --3way` leaves conflicts or fails, which leaves the fix in `<dir>/fix.patch` only. Resolve nothing, stop [Fold review fixes](#fold-review-fixes) and push nothing: tell the user, or, when the user does not follow the work, put the finding, where its fix now lives and the paths of `fix.patch`, and of `message` when one was saved, in your final report.

   Repeat this check until it lists none, then check the commits again, and fix a failure, as [Shape the history](#shape-the-history) says.
4. Push with `git push --force-with-lease`, then keep the body true: update every section the fixes changed, once, as `.claude/skills/pull-request/SKILL.md` > Update the body says.

## Merge

- **The user merges the pull request,** as `CLAUDE.md` > Workflow, "A branch reaches `main` only through a pull request whose CI passes" says.
- **After the merge,** keep the branch until the branches stacked on it have moved, as [Stack on an unmerged branch](#stack-on-an-unmerged-branch) says.
